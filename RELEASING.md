# Releasing Kepler

Two independent pipelines exist; **neither has ever been run**. The binaries pipeline is tag-driven; the npm one is
deliberately blocked until the gates below are changed by a maintainer. License: MIT (see `LICENSE`).

| Pipeline | Workflow | Trigger | Result |
|---|---|---|---|
| Native binaries | `.github/workflows/release-binaries.yml` | tag `vX.Y.Z` (or manual dry run) | **Published** GitHub Release with archives, `SHA256SUMS`, provenance attestations, autogenerated notes |
| Pi adapter on npm | `.github/workflows/release-npm.yml` | manual `workflow_dispatch` from tag `pi-vX.Y.Z`, plus environment approval | `npm publish --provenance` (blocked today) |

## Native binaries (`kepler` CLI/core)

Targets (native GitHub runners): `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`, `x86_64-apple-darwin`,
`aarch64-apple-darwin`, `x86_64-pc-windows-msvc`.

Assets (deterministic names, `<version>` = Cargo version without the `v`):

- `kepler-<version>-<target>.tar.gz` (Linux, macOS) and `kepler-<version>-<target>.zip` (Windows). Each contains one
  directory `kepler-<version>-<target>/` with `kepler` (`kepler.exe`), `LICENSE` and `README.md`.
- `SHA256SUMS`: `<sha256>  <asset>` for every archive. `install.sh` / `install.ps1` parse exactly this format.

Steps:

1. Make sure `main` is green (Rust CI, security, installers).
2. Bump `[workspace.package] version` in `Cargo.toml`, update `Cargo.lock`, merge.
3. Optional dry run: Actions -> "Release binaries" -> Run workflow (builds and uploads workflow artifacts only; no release, no attestation).
4. `git tag vX.Y.Z && git push origin vX.Y.Z` (or `git push --tags`). The tag must equal the `kepler-cli` version; the
   preflight job fails otherwise (and for non-semver tags).
5. The workflow builds 5 targets, smoke-tests (`kepler version`), packages, writes `SHA256SUMS`, attests provenance
   (`actions/attest-build-provenance`) and creates the GitHub Release.
6. **Published, not draft** (decision): the installers download `releases/latest`, which only resolves to published,
   non-prerelease releases. Tags with a suffix (`v0.2.0-rc.1`) become prereleases and are not "latest". The publishing job
   runs in the GitHub environment `release`: if you want a manual approval gate, add required reviewers to that
   environment (Settings -> Environments); without rules it publishes immediately. Create the environment and (optionally)
   restrict it to tags `v*` once.
7. Consumers verify with `sha256sum --check --ignore-missing SHA256SUMS` and `gh attestation verify <archive> --repo <owner>/<repo>`.

Caveats: binaries are not code-signed or notarized (macOS Gatekeeper / Windows SmartScreen will warn). Never move or
re-push a release tag; cut a new version instead. The workflow does not check that the tag is on `main`: tag from `main`.

## Pi adapter (`@kepler/pi`) on npm

AGENTS.md forbids publishing `adapters/pi` (and claiming it works) until Rust Core, hook integration, release tests, npm scope
ownership are approved (the license, MIT, is decided). `release-npm.yml` enforces this: its `guard` job runs
`.github/scripts/check-npm-release-gates.mjs` and **fails** while any of these hold:

- `adapters/pi/package.json` has `"private": true`
- `version` is `0.0.0`, no `test` script or no `test/*.test.*` files, install scripts or runtime dependencies present
- the run is not from tag `pi-v<version>`, `expected_version` differs, or the confirmation text is not exactly `publish <name>@<version>`

Manual steps pending before it can ever publish (each is a maintainer decision):

1. **Prove it works with real Pi**: an end-to-end test (currently only mock-core tests exist) and documented compatible Pi versions.
2. **Package name / npm scope**: reserve or confirm ownership of `@kepler` on npmjs.com, or pick another scope and update
   `package.json`, docs and workflows.
3. **License**: done (MIT, `LICENSE`); no longer a gate. Keep `package.json` `license` in sync.
4. **Trusted publisher**: on npmjs.com, package settings -> Trusted Publisher -> GitHub Actions, repository
   `<owner>/<repo>`, workflow `release-npm.yml`, environment `npm-release`. (A first publish of a brand-new package may need a
   one-time bootstrap by the owner; trusted publishing is configured per existing package.) No `NPM_TOKEN` is used or needed.
5. **GitHub environment**: create environment `npm-release` with required reviewers (and restrict it to tags `pi-v*`).
6. **Change the gates in a reviewed PR**: remove `"private": true` and set the real version.
7. **Tag**: `git tag pi-vX.Y.Z && git push origin pi-vX.Y.Z` (must equal `package.json` version).
8. **Run** Actions -> "Release npm (Pi adapter)" from that tag, with `expected_version` and
   `confirm` = `publish @scope/pi@X.Y.Z`; approve the `npm-release` environment prompt.
9. Verify the package page shows provenance, and install-test it (`pi install npm:<name>`).

Also pending for a real release: Core binary delivery and verification strategy for Pi users, changelog, and the acceptance
checklist in `docs/distribution/NPM_AND_PI.md`.

## Supply-chain hygiene

- Actions in the new workflows are pinned to commit SHAs (version in a trailing comment); Dependabot (`.github/dependabot.yml`) proposes updates.
- Default token permissions are `contents: read`; `contents: write`, `id-token: write` and `attestations: write` exist only in the release job (environment `release`), `id-token: write` only in the npm publish job.
- `security.yml` runs `cargo deny check` (see `deny.toml`) and `npm audit`.
- `ci.yml` pins its actions to commit SHAs as well (checked: no workflow uses a floating tag).
